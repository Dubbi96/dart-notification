## 1. 목적 · 왜 게이트인가

**아침 다이제스트**는 저녁 에디션 발행 푸시(19:05, DAR-523)와 별개로 **아침에 한 번 더** 요약을 배달하는 두 번째 일일 푸시 계열이다. 계획상 **게이트 백로그**(착수 금지·조건 개방) 항목이며, 개방 조건은 **"에디션 푸시 오픈율 2주 계측"**이다(계획 §4 게이트 백로그).

게이트인 이유:

- 두 번째 일일 푸시는 **알림 피로**를 두 배로 늘린다. 저녁 에디션조차 열리지 않는데 아침 푸시를 추가하면 옵트아웃·앱 삭제를 부른다.
- 프로젝트 원칙은 **PRICE_MOVE 동결(종류 확장 금지)**·**기본 OFF 보수적 신규 계열**이다(계획 §3 keep). 새 푸시 계열은 **수요 실증** 후에만 만든다.
- 따라서 아침 다이제스트 착수 여부는 **저녁 에디션 푸시가 실제로 열리고, 옵트인이 유지되는가**라는 정량 근거에 종속시킨다.

**본 문서의 역할**: 2주 후 판정이 자의적이지 않도록, 판정에 쓸 **지표·임계값·측정 기간·판정 절차·no-go 대안**을 착수(계측 시작) *이전에* 확정한다. 임계값은 오너 승인 대상이다(§7).

## 2. 개방 전제조건 (2주 클록 시작 조건)

측정 클록은 아래가 **모두** 참인 첫 거래일부터 카운트한다. 하나라도 거짓이면 클록은 시작되지 않는다(계측 대상 부재 = 조기 판정 금지).

| # | 전제 | 확인 방법 (결정론) |
|---|------|--------------------|
| P1 | 저녁 에디션 푸시가 **프로덕션에서 라이브** | `push_delivery_log` 에 `type='EDITION' AND status='SENT'` 행이 프로덕션에 1건 이상 존재하는 첫 거래일 = **라이브 앵커(D0)**. |
| P2 | 테스터 코호트 **온보딩 완료** | 테스터 클록 7/22(계획 §5.2) 이후 · `tester_events` 에 코호트 사용자 활동 존재. |
| P3 | 계측 코드가 **테스터 단말 번들에 동승** | DAR-516 계측은 클라 번들 포함 — 계측 반영 APK 재빌드 완료(analytics 문서 §8). 재빌드 전이면 이벤트가 발화하지 않아 오픈율이 구조적 0(가짜 no-go)이 된다. |
| P4 | `editionPushEnabled` **옵트인 경로가 테스터에게 노출** | 설정 센터 v2(DAR-514) 라이브 · 최소 1인 이상 `editionPushEnabled=true`(기본 OFF라 명시적 옵트인 없으면 발송 0 → P1도 미충족). |

> **앵커 정의**: D0 = P1~P4 전부 참인 첫 거래일. 측정창 = D0부터 **10 거래일(≈2주)**. 캘린더 날짜가 아니라 **첫 SENT EDITION 행**으로 self-define 하므로, 배포 지연이 판정을 오염시키지 않는다. 시점 앵커는 계획 §6(M10 졸업 ≈8/5)과 정합하되, 본 게이트는 그와 독립적으로 D0 기준으로 흐른다.

## 3. 계측 지표 정의 — **현재 계측 가능한 것만** (수용기준 1)

각 지표는 **소스(테이블/엔드포인트/필드)**를 명시한다. 아래 소스 밖의 데이터는 쓰지 않는다.

### 3.1 발송 건전성 (send health) — 소스: `push_delivery_log`

에디션 푸시가 **실제로 발화하고 옵트인 사용자에게 도달**하는지. 다이제스트가 요약할 대상(에디션)이 존재해야 게이트가 의미를 갖는다.

- **M1 발송일 커버리지** = 측정창 10 거래일 중 `type='EDITION' AND status='SENT'` 행이 ≥1건인 **거래일 수**.
  ```sql
  SELECT COUNT(DISTINCT "kstDate")
  FROM push_delivery_log
  WHERE type = 'EDITION' AND status = 'SENT'
    AND "kstDate" BETWEEN :d0 AND :d0_plus_9;  -- YYYYMMDD
  ```
- **M2 캡 억제율** = `SUPPRESSED_CAP / (SENT + SUPPRESSED_CAP)` (type='EDITION', 측정창). 이미 피로 상한(dailyPushCap)에 눌리고 있으면 아침 푸시 추가는 역효과.
- **M3 회당 고유 수신자** = 에디션 1호(refId=editionDate)당 `COUNT(DISTINCT userId)` SENT. 옵트인 규모의 실측.

> 정직 한계: `push_delivery_log` 의 SENT 는 **캡 게이트 통과(=발송 시도 허용) 시점**에 기록된다 — FCM 실배달 영수증이 아니다(영수증 e2e 는 DAR-521 에서 별도 검증, 본 테이블에 회당 적재되지 않음). 따라서 M1~M3 는 **"발송 시도"** 기준의 하한 관측치다.

### 3.2 코호트 참여 (engagement) — 소스: `GET /ops/tester-metrics`

DAR-516 tester-metrics 가 산출하는 **코호트 고유 사용자** 비율(관측창 `days` 파라미터 = 측정창 일수).

- **M4 코호트 에디션 오픈율** = `data.openRate` = `editionOpenUsers / totalUsers`. 측정창 내 `edition_open` 을 1회 이상 발화한 고유 사용자 비율.
- **M5 코호트 푸시 오픈율** = `pushOpenUsers / totalUsers`(응답의 `pushOpenUsers`·`totalUsers` 로 파생). 측정창 내 `push_open`(푸시 탭 앱 진입) 발화 고유 사용자 비율.
- **M6 재방문율** = `data.revisitRate` = 활동일(KST) ≥2 인 고유 사용자 비율. 다이제스트가 노리는 **반복 소비 리듬**의 직접 대리지표.

### 3.3 옵트인 지속 (retention of consent) — 소스: `notification_settings.editionPushEnabled`

`editionPushEnabled` 는 **기본 OFF(opt-in)** 이다(DAR-514 스키마). 따라서 의미 있는 측정은 "**옵트인 비율**"이며, 옵트아웃은 **두 시점 스냅샷의 차분**으로만 관측한다(§4 한계 참조).

- **M7 옵트인 스냅샷** = `editionPushEnabled=true` 사용자 / 코호트 활성 사용자. **D0 근방(주 1)**·**측정창 종료(주 2)** 2회 스냅샷.
  ```sql
  SELECT
    COUNT(*) FILTER (WHERE "editionPushEnabled") AS opted_in,
    COUNT(*)                                     AS total
  FROM notification_settings
  WHERE "userId" IN (:cohort_user_ids);
  ```
- **M8 순 옵트아웃 신호** = `(opted_in@주1 − opted_in@주2) / opted_in@주1`. 양수(옵트인 감소)이면 이탈 신호. 개인별 이탈은 귀속 불가(§4).

## 4. 계측 한계 — "DAR-516 이벤트 로깅 연동 확인" (수용기준 1)

착수 전 반드시 인지할 **구조적 한계**. 판정은 이 한계 위에서 이뤄지므로, 오너에게 명시 회부한다(§7).

| 한계 | 원인 (코드 근거) | 판정에 대한 영향 |
|------|-----------------|------------------|
| **회당(per-send) 에디션 푸시 오픈율은 계측 불가** | ① `push_open`(tester_events)은 **푸시 종류 무관** — `useNotificationSetup` 리스너·콜드스타트에서 임의 푸시 탭에 발화(에디션 전용 아님). ② tester_events 에 messageId/refId 없음 → **특정 SENT 행 ↔ open 이벤트 상관 불가**. | 계획 문구 "푸시 오픈율"의 문자적(회당) 계측은 없다. 대신 **코호트 대리지표 M4·M5·M6** 로 판정한다. |
| **에디션 오픈이 푸시 유래인지 분리 불가** | `edition_open` 은 **신호탭 날짜선택 + 홈 최신 에디션 요약** 양쪽에서 발화(analytics §4) — 푸시 탭 유래로 한정 불가. | M4 는 "에디션을 봤다"이지 "푸시로 열었다"가 아니다 — 상한 관측치. 딥링크(DAR-527)가 향후 상관 훅. |
| **개인별 옵트아웃 이력 없음** | `notification_settings` 는 **현재 상태 + `updatedAt`** 만(토글 이벤트 로그 없음). tester_events 화이트리스트에도 설정 토글 이벤트 없음. | 옵트아웃은 **두 스냅샷 차분(M8)** 으로만 관측 — 누가 언제 껐는지·"켰다 껐다"는 불가. |
| **표본 n≈12 → 신뢰구간 넓음** | 코호트 12인(계획 §5.2). | 모든 비율은 **방향성 게이트**이지 통계적 유의가 아니다 — 프로젝트 n≥30 정직 규약(계획 §2)과 동일 태도. 임계값은 "명백한 실패/성공" 경계로만 쓴다. |

**결론(연동 확인)**: DAR-516 이벤트 로깅으로 **발송 볼륨(M1~M3)·코호트 참여(M4~M6)·옵트인 스냅샷(M7~M8)** 은 계측 가능하다. **회당 푸시 오픈율은 계측 불가**하므로, 본 게이트는 그 대리지표로 판정하도록 재정의했다. (회당 계측이 판정 요건이라면 §8 no-go 대안 A의 선행 계측 보강이 필요.)

## 5. 임계값 제안 + 근거 (수용기준 2)

n≈12 방향성 게이트다. **go = 아래 필수(MUST) 전부 충족 + 권고(SHOULD) 과반**. 하나라도 필수 미달이면 **no-go 또는 오너 회부**. 임계값은 **제안**이며 오너 승인 대상(§7).

| 지표 | 임계값(제안) | 등급 | 근거 |
|------|-------------|------|------|
| M1 발송일 커버리지 | ≥ 8 / 10 거래일 | MUST | 요약할 에디션이 대부분의 날 존재해야 다이제스트가 성립. <8이면 에디션 밀도 문제(A3/DAR-513 폴백)가 선결과제 — 다이제스트 이전. |
| M2 캡 억제율 | < 10% | MUST | 이미 피로 상한에 눌리면 두 번째 푸시는 순 억제만 늘린다. 캡(기본 30)은 정상량을 크게 상회하므로 10% 초과는 이상 신호. |
| M7 옵트인 스냅샷(주2) | ≥ 50% (≥6/12) | MUST | **기본 OFF(opt-in)** 계열에서 과반이 저녁 에디션을 **자발적으로 켰다**는 것이, 두 번째 일일 푸시를 정당화하는 최소 수요 실증. 과반 미만이면 첫 계열 수요부터 미검증. |
| M8 순 옵트아웃 | ≤ 20% | MUST | 주1→주2 옵트인 20% 초과 감소는 **피로 이탈** 진행 신호 — 푸시 추가 금지. |
| M4 코호트 에디션 오픈율 | ≥ 50% | SHOULD | 활성 테스터 과반이 측정창에 에디션을 최소 1회 봄 = 콘텐츠 관련성 하한. (푸시 유래 분리는 불가 — §4.) |
| M5 코호트 푸시 오픈율 | ≥ 30% | SHOULD | 활성 테스터 3인 중 1인 이상이 임의 푸시를 탭 = 푸시 채널 자체의 반응성 하한. 종류 무관 대리(§4). |
| M6 재방문율 | ≥ 40% | SHOULD | 활동일 ≥2 과반 근접 = 다이제스트가 노리는 반복 리듬의 근거. 저조하면 배달 빈도↑가 리듬을 만들지 못한다는 반증. |

> 임계값 산정 태도: 절대 벤치마크(업계 푸시 오픈율 등)는 표본·맥락이 달라 직접 인용하지 않는다. 대신 **"두 번째 일일 푸시를 추가해도 순효용이 양(+)일 최소 조건"**을 코호트 내부 기준으로 잡았다 — ① 요약 대상 존재(M1/M2), ② 첫 계열 수요 실증(M7/M8), ③ 콘텐츠·채널·리듬 반응(M4/M5/M6). MUST 3종(발송·옵트인·이탈)은 **수요와 피로의 순증 방지**라 하드, SHOULD 3종은 참여 품질이라 소프트로 배치했다.

## 6. 측정 기간 · 판정 절차

- **측정 기간**: D0(§2 앵커)부터 **10 거래일(≈2주)**. 주말·휴장은 카운트 제외(에디션 발행은 평일 `5 19 * * 1-5`).
- **스냅샷**: M7 옵트인은 **D0+0~1(주1)**·**D0+9(주2)** 2회. 나머지 지표는 종료 시점 1회 집계(관측창 = 측정창 일수).
- **판정 실행(결정론)**: 측정창 종료 익영업일에 아래를 실행해 수치 표(§5 컬럼) 를 산출한다.
  1. `GET /ops/tester-metrics?days=<측정창 일수>` → M4·M5·M6.
  2. §3.1 SQL → M1·M2·M3.
  3. §3.3 SQL(주1·주2 스냅샷) → M7·M8.
- **회부**: 산출된 수치 표 + 본 문서 §5 임계값을 **오너에게 회부**(계획 §5.3 "Wave B 다이제스트 go/no-go 기준 승인"). 오너가 go/no-go 확정.

## 7. 오너 판정 항목 (수용기준 3)

아래는 **오너 결정**이며 에이전트가 자율 확정하지 않는다.

1. **임계값 승인/조정** — §5 제안 임계값(특히 MUST 3종: M1≥8, M7≥50%, M8≤20%)을 확정하거나 조정.
2. **회당 계측 요건 여부** — §4 한계상 회당 푸시 오픈율은 불가. 코호트 대리지표(M4~M6)로 **충분한지**, 아니면 §8 대안 A(선행 계측 보강)를 요구할지.
3. **표본 판정** — n≈12 방향성 결과를 근거로 착수할지, **표본 확대(테스터 증원·측정창 연장) 후 재판정**할지.
4. **MUST 부분 충족 시 처리** — MUST 일부만 미달일 때 no-go 확정 vs 조건부(대안 후 재측정).
5. **에디션 밀도 연계** — M1<8(발송 커버리지 부족)이 에디션 밀도 실측(A3/DAR-513) 결과와 겹치면, 다이제스트보다 **밀도 폴백**을 선결로 둘지(계획 §5.3 A3 판정과 동시 회부).

## 8. no-go 시 대안

no-go(또는 판정 보류)여도 **아침 다이제스트 코드 착수 0**을 유지하며, 아래 중 오너가 택일:

- **대안 A — 계측 보강 후 재측정**: 회당 오픈율을 원하면, 에디션 딥링크(DAR-527)에 캠페인/메시지 식별자를 실어 **푸시 탭 → edition_open 상관**을 최소 계측으로 추가(별도 이슈). 그 후 동일 게이트 재적용.
- **대안 B — 측정창 연장/표본 확대**: 방향성만 잡혀 결론 불가면 측정창을 4주로 연장하거나 테스터를 증원해 재판정.
- **대안 C — 계열 무증설, 저녁 에디션 강화**: 두 번째 푸시 대신 **기존 저녁 에디션의 콘텐츠·본문(한 줄 판단, DAR-525)·딥링크** 품질에 재투자. 알림 종류 무증설 원칙(계획 §3)과 정합.
- **대안 D — 게이트 유지(무기한 백로그)**: 조건 미개방 시 게이트 백로그에 그대로 존치. 재개방 트리거 = 저녁 에디션 옵트인·오픈율이 임계값을 넘어서는 후속 관측.
