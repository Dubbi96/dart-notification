## 1. 역할 정의 & 책임 범위

### 이 파트가 소유하는 것

- **테스트 전략 수립** — 전체 마일스톤(M0~M12)에 걸친 단위/통합/E2E 테스트 계획 및 커버리지 기준
- **회귀 체크포인트(↩︎) 게이트 운영** — `01-execution-roadmap.md`의 각 단계 ↩︎ 항목을 실제 측정 가능한 기준으로 변환하고, 통과/차단 판정
- **go/no-go 졸업 게이트** — M9 백테스트 검증(R), M10 MVP 졸업(R), M11 반자동매매 진입(R), M12 자동매매 최종 허가(R)
- **AI 금지영역 감사** — 코드 레벨·런타임 로그에서 AI가 최종 주문 승인·손익 하드룰·포트폴리오 한도·주문 수량·리스크 우회 결정에 개입했는지 추적
- **전역 회귀 매트릭스 점검** — FK 정합(rcpNo/corpCode)·마이그레이션·테스트 그린·AI 비용 기록·보안을 매 마일스톤 종료 시 일괄 확인

### 다른 파트와의 경계

| 경계 | 내용 |
|------|------|
| **BE와의 경계** | BE가 로직·API를 구현 → QA가 검증 기준 정의 + 테스트 작성 또는 리뷰. 테스트 코드 의무 작성은 BE; QA는 커버리지 및 설계 적합성 검토 |
| **DQ와의 경계** | DQ가 Score 공식·Event Study 구현 → QA가 lookahead 감사·표본 충분성·통계 일관성 검증 |
| **AI와의 경계** | AI 파트가 프롬프트·출력 스키마 관리 → QA가 AI 금지영역 침범 여부·비용 기록 누락 감사 |
| **인프라와의 경계** | 인프라가 CI/CD·관측성 파이프라인 구성 → QA가 CI 그린 기준(테스트 통과율) 정의 |
| **기획 파트와의 경계** | 화면·시나리오·정책 기획이 요구사항 정의 → QA가 요구사항 대비 실제 동작 검증 |

## 2. 마일스톤별 업무 (M0~M12)

### M0 — 기준선 & 수집 안정화 [C 협업]

**역할:** 진입 게이트 측정 기준 수립, 기존 코드 회귀 베이스라인 확보

- [ ] 수집 성공률 측정 방법 정의: `DisclosureCollectionLog.status` 집계 쿼리 작성 (SUCCESS/(SUCCESS+PARTIAL+FAILED) ≥ 95%)
- [ ] 중복 저장 0건 검증 쿼리: `SELECT rcpNo, COUNT(*) FROM disclosures GROUP BY rcpNo HAVING COUNT(*) > 1`
- [ ] 기존 기능 회귀 베이스라인 체크리스트 작성 (카카오 로그인·관심목록·알림·푸시·딥링크)
- [ ] 스키마 변경 후 기존 마이그레이션 재현 가능성 검증: `prisma migrate deploy` 클린 환경 테스트
- [ ] **진입 게이트 판정:** 수집 성공률 ≥ 95% · 중복 0 · 5종 공시 필터 동작 확인 → go/no-go 판정 문서 작성

### M1 — 공시 원문 파싱 [C 협업]

**역할:** 파싱 정확도 검증 기준 설정, 표 추출 누락율 측정 방법 정의

- [ ] 파싱 성공률 측정 쿼리: `DisclosureDocument.parseStatus = 'SUCCESS'` 비율, 5종 공시 표본 100건 기준 ≥ 90%
- [ ] `isAmendment` 정확 판정 테스트 케이스 설계: 정정공시 rcpNo 10건 수동 샘플링 후 DB 값 대조
- [ ] 표 누락 비율 추적 체계 정의: `parsedJson` 내 테이블 배열 길이 0 건수 집계
- [ ] **↩︎ M0 회귀 확인:** 신규 공시 수집 후 파싱 큐 누락 없는지(CollectionLog.newlySaved vs DisclosureDocument 건수 delta ≤ 허용 지연), 수집 SLA 95% 유지 확인
- [ ] **진입 게이트 판정:** 파싱 성공률 ≥ 90% · isAmendment 정확도 수동 검증 → pass/fail 기록

### M2 — 이벤트·수치 추출 [C 협업]

**역할:** 이벤트 분류 정확도·수치 추출 정확도 수동 검증, 표 누락 전파율 측정

- [ ] 이벤트 분류 정확도 측정: 5종 이벤트별 20건씩 총 100건 수동 정답 라벨링 → Rule 분류 결과 대조 ≥ 90%
- [ ] 핵심 수치 추출 정확도 측정: `salesRatio`, `dilutionRate` 등 파생값을 원문 수기 계산과 대조 ≥ 85%
- [ ] 표 누락 → 수치 추출 실패 전파율: parseStatus='FAILED' 공시 중 DisclosureEvent 미생성 비율 측정
- [ ] **↩︎ M1 회귀 확인:** 표 누락이 M2 수치 추출 실패로 전파되는 비율이 임계치(예: 15%) 초과 시 M1 파서 보강 요청
- [ ] **↩︎ M0 회귀 확인:** 신규 공시 유형 변화가 5종 분류 게이트에 영향 없는지 점검
- [ ] **진입 게이트 판정:** 분류 정확도 ≥ 90% · 수치 추출 정확도 ≥ 85% → pass/fail 기록

### M3 — AI Analyst + 비용계측 토대 [C 협업]

**역할:** AI 출력 품질 검증, AI 금지영역 침범 1차 감사, 비용 기록 정합성 확인

- [ ] AI 분석 10건+ JSON 유효성 검증: `outputJson` 스키마 체크(필수 키 존재·타입), 파싱 실패 fallback 동작 확인
- [ ] `AIUsageLog` 기록 완전성 감사: AI 호출 1회당 로그 1건 생성 확인, 누락 0 검증 쿼리
- [ ] 공시 1건당 평균 비용 측정: `SELECT AVG(costUsd) FROM ai_usage_logs WHERE DATE(createdAt)=오늘` < $0.005
- [ ] L0(AI 미사용) 비율 검증: 전체 공시 대비 AIUsageLog 있는 공시 비율 ≤ 30% (= L0 ≥ 70%)
- [ ] **AI 금지영역 1차 코드 감사:** AiAnalystService 출력이 주문 수량·손익 하드룰 결정에 직접 사용되지 않는지 코드 리뷰
- [ ] **↩︎ M2 회귀 확인:** AI 이벤트 타입 보정 결과 vs Rule 분류 불일치율 추적; 불일치율 > 20% 시 M2 룰 재점검 요청
- [ ] **↩︎ M1 회귀 확인:** 프롬프트 토큰량 모니터링으로 원문 전문 통째 입력 여부 감지; 토큰 > 2,000/건이면 M1 추출 강화 요청
- [ ] **진입 게이트 판정:** JSON 정상 · fallback 동작 · 평균 비용 < $0.005 · L0 ≥ 70% → pass/fail

### M4 — 시세 데이터 (KRX) [C 협업]

**역할:** 시세 데이터 결측률 측정, 지표 계산 정확도 수기 검증, 거래일 캘린더 정합 확인

- [ ] 관심 50종목 일봉 결측률 측정: `SELECT corpCode, COUNT(*) FROM stock_daily_prices WHERE tradeDate BETWEEN ... GROUP BY corpCode` 결측 < 2%
- [ ] 지표 계산 정확도 수기 검증: MA5/MA20/RSI14 값을 엑셀 수계산 결과와 3종목 이상 대조
- [ ] 공시 `rcpDt` vs 가격 거래일 캘린더 정합 확인: 휴장일 공시에 대응 가격 날짜가 올바른 거래일로 보정되는지 5건 수동 확인
- [ ] `Company.stockCode` 오매핑 확인: 시세 매핑 실패(stockCode=null 또는 매핑 없음) 비율 측정 → 빈 값 건수 보고
- [ ] **↩︎ M0 회귀 확인:** Company.stockCode/market 정확도 재점검; 시세 매핑 실패율 > 5% 시 seed 보완 요청
- [ ] **진입 게이트 판정:** 결측률 < 2% · 지표 수기 검증 통과 · 선행상승률 산출 정상 → pass/fail

### M5 — Event Study [C 협업]

**역할:** Event Study 통계 신뢰성 감사, 라벨 오류율·표본 충분성 점검

- [ ] 5종 이벤트 표본 충분성 확인: 이벤트별 표본 ≥ 50건, 표본 수와 분산 함께 `EventStudyResult`에 기록되는지 확인
- [ ] D+5 통계 유의성 체크: 표본 < 30건인 이벤트·버킷에 "표본 신뢰 강등" 플래그 부여 규칙 검증
- [ ] 가격 데이터 결측 → 통계 왜곡 감사: 결측 종목이 통계 계산에서 제외/보정됐는지 확인
- [ ] 라벨 오류율 영향 추적: M2 이벤트 분류 오류율 > 15%인 이벤트 타입의 Event Study 결과에 신뢰등급 하향 기록
- [ ] **↩︎ M4 회귀 확인:** 가격 데이터 결측이 표본 신뢰 강등 규칙 없이 통계에 포함되지 않는지
- [ ] **↩︎ M2/M3 회귀 확인:** 이벤트 라벨 정확도가 통계 신뢰도에 미치는 영향 문서화
- [ ] **진입 게이트 판정:** 이벤트별 표본 ≥ 50건 · 표본수/분산 기록 · 결측 처리 규칙 명문화 → pass/fail

### M6 — 매수 Signal Engine [C 협업]

**역할:** 신호 등급 분포 검증, Event Study 반영 여부 확인, 차트 지표 최신성 점검

- [ ] Buy Score 등급 분포 검증: 전체 TradingSignal 중 BUY_CANDIDATE(≥60) 비율이 0% 또는 100%가 아닌지(합리적 분포) 히스토그램 확인
- [ ] 가중치 config화 추적: `signal-config.ts` 변경 이력이 git에 남고, 점수 변화가 재현 가능한지 확인
- [ ] Event Study 반영 감사: 표본 부족 이벤트(< 50건)의 가중 감쇠가 Buy Score에 실제 적용되는지 코드 확인
- [ ] 차트 지표 최신성 확인: BuySignalService가 오늘 날짜 기준 최신 StockDailyPrice를 참조하는지, 지연 있으면 경고
- [ ] **↩︎ M5 회귀:** Event Study 통계가 점수에 실제 반영되는지 + 표본 부족 감쇠 동작 확인
- [ ] **↩︎ M3 회귀:** Persona 해석 AI polarity와 최종 Buy Score 방향 일치 여부 10건 샘플 검증
- [ ] **진입 게이트 판정:** 자동 계산·저장 · 등급 분포 합리적 · 가중치 config 추적 → pass/fail

### M7 — Position Thesis [C 협업]

**역할:** Thesis 자동생성 1:1 정합 검증, invalidConditions 기계 평가 가능성 감사

- [ ] 매수 후보 생성 시 Thesis 빠짐없이 자동생성 확인: TradingSignal(BUY_CANDIDATE) 건수 vs PositionThesis 건수 1:1 정합 쿼리
- [ ] `invalidConditions` 추상 문장 금지 감사: invalidConditions 배열의 각 조건이 DB 필드 또는 수치 기준으로 평가 가능한 형태인지 수동 리뷰 10건
- [ ] Thesis 생명주기 정상성 확인: ACTIVE→INVALIDATED→EXITED 상태 전이 시 `invalidatedAt`, `invalidReason` 필드 정상 기록 여부
- [ ] **↩︎ M6 회귀:** BUY 신호와 Thesis 자동연결 정합(신호당 Thesis 1:1) 재확인
- [ ] **진입 게이트 판정:** Thesis 자동생성 100% · invalidConditions 기계 평가 가능 → pass/fail

### M8 — Portfolio & Exit Engine [C 협업]

**역할:** Exit Score 성능·정확도 검증, thesis-driven exit 동작 확인, 하루 3회 점검 스케줄 감사

- [ ] Exit Score 일괄 점검 성능: 50 포지션 기준 ≤ 60초 이내 완료 측정 (cron 로그에서 실행 시간 추출)
- [ ] 손절/논리훼손 트리거 동작 확인: invalidConditions 충족 시 ExitSignal.exitAction = 'EXIT' 자동 발동 테스트
- [ ] thesis-driven exit 동작 감사: PositionThesis.invalidConditions가 ExitSignalService에서 실제 평가되는지 코드 리뷰 + 3건 시나리오 테스트
- [ ] 하루 3회 점검 스케줄 정확성: 09:00/13:00/16:30 cron이 실제 실행되는지 CollectionLog 패턴으로 확인
- [ ] **↩︎ M7 회귀:** PositionThesis.invalidConditions가 Exit 점검에서 평가되는지
- [ ] **↩︎ M4 회귀:** 차트 훼손 감지(20일선 이탈·전저점 이탈)가 최신 StockDailyPrice 기반으로 동작하는지
- [ ] **↩︎ M1 회귀:** 하루 3회 점검이 당일 신규 정정공시(악재)를 반영하는지 DisclosureEvent.isAmendment 처리 흐름 확인
- [ ] **진입 게이트 판정:** 60초 내 완료 · 손절/논리훼손 트리거 정상 · thesis-driven exit 작동 → pass/fail

### M9 — 백테스트 [R 주담당]

**역할:** lookahead bias 감사, 3구간 테스트 결과 검증, 비용 반영 확인, MDD 기준 판정

- [ ] **Lookahead bias 감사** — BacktestRun에서 각 시점 t의 신호·Exit 결정이 t+1 이후 데이터(미래 가격·AI 출력·공시)를 참조하지 않는지 코드 레벨 검토. 특히:
  - BuySignalService가 `tradeDate > rcpDt` 기준 가격만 사용하는지
  - EventStudyResult가 D0 이후 통계만 반영하는지
  - AI 분석 결과 타임스탬프가 공시 시각 이후인지
- [ ] **3구간 테스트 결과 검증** — 상승장(예: 2023년 1~6월 코스피 +12%)·하락장(예: 2022년)·횡보장 각각 BacktestRun 결과 확인:
  - 3구간 모두 비용(수수료 0.015% 매수·0.3% 매도·세금) 반영 후 수익 > 0
  - MDD ≤ -15% 확인
  - 단일 종목·이벤트 의존도 점검(상위 1개 종목 기여도 < 50%)
- [ ] **비용 반영 완전성 감사** — BacktestTrade에 수수료·세금·슬리피지·거래정지·상하한가·부분체결 각 항목이 반영되는지 코드 확인
- [ ] **이벤트별 표본 충분성** — 5종 이벤트 각 표본 ≥ 30건 확보 확인, 부족 이벤트는 결과에 "표본 부족" 경고 명기
- [ ] **최악 거래 10개 분석** — BacktestRun 결과에서 손실 상위 10건 원인 분류(lookahead 오류/룰 오류/데이터 오류/실제 전략 실패) 보고
- [ ] **↩︎ M6/M8 회귀:** Signal·Exit 룰이 과거 시점 데이터만으로 재현되는지 lookahead 재확인
- [ ] **↩︎ M5 회귀:** Event Study 통계와 백테스트 성과 일관성 비교; 괴리 > 10%p면 한쪽 결함으로 보고
- [ ] **↩︎ M4 회귀:** 과거 가격 데이터 기간·품질 충분성 재확인
- [ ] **진입 게이트 판정 기준:**
  - 3구간 모두 테스트 완료
  - 비용 반영 후 수익 > 0
  - MDD ≤ -15%
  - 한두 종목 의존 아님
  - 이벤트별 표본 충분
  - lookahead 0건 확인
  → **go/no-go 보고서 작성 후 팀 확정**

### M10 — 모의투자 + 비용 거버넌스 완성 [R 주담당 — ★ MVP 졸업 게이트]

**역할:** 전 파이프라인 E2E 회귀, 30일+ 운용 성과 집계, MVP 졸업 5대 지표 판정

#### 전 파이프라인 E2E 회귀 테스트
- [ ] **엔드-투-엔드 흐름 검증:** 수집(M0) → 파싱(M1) → 이벤트 추출(M2) → AI 분석(M3) → 시세(M4) → 통계(M5) → 매수 신호(M6) → Thesis(M7) → Exit(M8)이 실시간으로 끊김 없이 연결되는지 확인. 각 단계 산출물 건수 정합 확인 쿼리 작성
- [ ] 단위/통합 테스트 전부 그린 확인: CI 파이프라인 최종 실행 결과 캡처
- [ ] AI 추정 비용 vs 실측 비용 일치 검증: `AIUsageLog.costUsd` 합계 vs LLM API 청구 내역 대조 (오차 ≤ 5%)
- [ ] 백테스트 체결가 가정 vs 모의 실측 괴리 측정: BacktestTrade 체결가 vs PaperTrade 실측 체결가 평균 괴리 기록

#### 30일+ 운용 성과 집계 (MVP 졸업 5대 지표)
- [ ] **신호 적중률** 측정: BUY_CANDIDATE 신호 발생 후 D+5 수익률 > 0% 비율 쿼리 작성 → 목표 ≥ 55%
- [ ] **모의 누적 수익률** 측정: `PaperTrade` 전체 손익 / 초기 가상 원금 계산 → 목표 > 0%
- [ ] **AI비용/모의순익 비율** 실측: `AIUsageLog` 총 costUsd / PaperTrade 순익(원→USD 환산) → 목표 ≤ 20%
- [ ] **Exit 정확도** 측정: EXIT 액션 후 D+3 추가 하락 확인 비율 → 목표 ≥ 50%
- [ ] **수집 성공률** 최종 확인: CollectionLog 기준 ≥ 95%
- [ ] **AI 금지영역 침범 0건 최종 감사:** TradingAuditLog(M11 전 로그) + AIUsageLog + 코드에서 AI가 주문 승인·하드룰·한도·수량·리스크 우회 결정에 개입한 흔적 0 확인
- [ ] **go/no-go 보고서 작성:** 5대 지표 모두 충족 시 "MVP 졸업 선언" · 미충족 시 원인 분석 후 재설계 근거 문서화

### M11 — 반자동매매 [R 주담당]

**역할:** 실주문 멱등성·Risk veto 동작 검증, 전 주문 audit 기록 완전성 감사

- [ ] **주문 멱등성 검증:** 동일 신호에 대해 중복 OrderRequest가 생성되지 않는지 멱등 키 로직 테스트
- [ ] **Risk 사전체크 6항목 검증:**
  - [ ] 1회 주문 비중 한도 초과 차단
  - [ ] 단일 종목 비중 한도 초과 차단
  - [ ] 일별 손실 한도 초과 차단
  - [ ] 관리종목·투자위험 종목 자동 차단
  - [ ] 시장 급락(코스피 -3% 이상) 신규 매수 중단
  - [ ] API 오류 상태에서 주문 차단
- [ ] **AI는 주문 승인 불가 확인:** OrderRequest 승인 경로에서 AI 출력이 최종 승인 판단에 개입하지 않는지 코드 감사. AI는 권고(scoreBreakdown, riskFactors)만 제공하고 승인 버튼은 사용자만 가능
- [ ] **TradingAuditLog 완전성:** 모든 주문(승인·거절·취소)이 audit 기록되는지, 누락 0건 확인
- [ ] 소액 실주문 정확 체결 확인: 테스트 계좌 1건 실행 후 OrderExecution.execPrice·execQty가 증권사 내역과 일치
- [ ] **↩︎ M10 회귀:** 모의에서 검증된 신호·Exit 로직이 실주문 경로에서 동일하게 동작하는지 코드 diff 확인
- [ ] **진입 게이트 판정:** 멱등·체결 정확 · audit 완전 · Risk 6항목 통과 · AI 승인 불가 확인 → pass/fail

### M12 — 제한적 자동매매 [R 주담당]

**역할:** 이벤트 화이트리스트 준수 검증, 하드 리스크 룰 자동중단 동작 테스트, Kill Switch 검증

- [ ] **이벤트 화이트리스트 검증:** 자동매매 허용 이벤트(자기주식취득·소각 / 대규모공급계약 / 배당확대 / 실적서프라이즈 / 악재해소 5종)만 자동 주문 생성되는지 확인. 블랙리스트 9종(유상증자/CB/감사의견/거래정지·상폐/소송·횡령·배임/관리종목/초저유동성/정치·테마급등) 입력 시 주문 생성 차단 테스트
- [ ] **하드 리스크 룰 자동중단 테스트:**
  - [ ] 1회 주문 > 3% 포트폴리오: 주문 거부
  - [ ] 단일 종목 > 10%: 주문 거부
  - [ ] 1일 최대손실 -2% 도달: 신규 매수 중단
  - [ ] 1주 최대손실 -5% 도달: 전략 일시중단
  - [ ] 연속손실 N회: 자동중단 트리거
  - [ ] 시장 급락(코스피 -3%): 신규 매수 중단
  - [ ] 증권사 API 오류: 주문 중단
- [ ] **Kill Switch 검증:** 수동 Kill Switch 활성화 시 진행 중인 주문 취소 + 신규 주문 생성 차단 + 상태 audit 기록 확인
- [ ] **Risk veto 우선성 확인:** AI 분석이 POSITIVE/BUY_CANDIDATE여도 Risk Engine 거부 시 주문 미생성 확인 (AI override 0건)
- [ ] **M9/M10 졸업 조건 재확인:** 해당 이벤트가 백테스트(3구간 통과)·모의투자(90일, 누적 > 0%, AI비용/순익 ≤ 10%) 통과 여부 재점검
- [ ] **↩︎ M11 회귀:** 반자동에서 안정적이었던 전략만 자동화 후보임을 승인 이력으로 확인
- [ ] **자동매매 졸업 게이트 최종 판정:**
  - 90일 모의 누적수익 > 0%
  - AI비용/순익 ≤ 10%
  - 백테스트 3구간 통과
  - Exit 정확도 ≥ 55%
  - 점진 롤아웃(소액 → 확대) 진입 허가
  → **go/no-go 최종 보고서 작성**

## 5. 역할 특화 표준·체크리스트

### 5-1. 테스트 레벨 정의

| 레벨 | 범위 | 담당 | 기준 |
|------|------|------|------|
| **단위 테스트** | 서비스 메서드·Score 공식·파서 함수 | BE·DQ 작성, QA 리뷰 | 핵심 서비스 커버리지 ≥ 80% |
| **통합 테스트** | API 엔드포인트·DB 쓰기·외부 API 모킹 | BE 작성, QA 리뷰 | 전 엔드포인트 최소 1건 happy path |
| **E2E 시나리오** | 공시 수집→알림·공시→매수신호→모의거래 전체 흐름 | QA 주도 설계·실행 | M10 전 파이프라인 1회 이상 완주 |
| **회귀 테스트** | 이전 마일스톤 단위/통합 테스트 재실행 | CI 자동화 + QA 결과 확인 | 매 마일스톤 종료 시 100% 통과 |

### 5-2. AI 금지영역 감사 체크리스트 (매 마일스톤 적용)

다음 경로에서 AI 출력이 직접 사용되는지 코드 검색:

```
# 감사 항목
- [ ] OrderRequest.approve() 또는 주문 실행 트리거에 AI 리턴값 직접 바인딩 없음
- [ ] stopLossRule.hardStop 수치가 AI 출력에서 오지 않음 (PositionThesis.stopLossRule은 Rule에서 계산)
- [ ] maxWeightPct 값이 AI 출력에서 결정되지 않음
- [ ] 주문 수량(quantity) 계산이 AI 출력과 무관함
- [ ] Risk Engine(veto)이 AI polarity와 무관하게 독립 실행됨
```

위반 발견 시: **즉시 개발 중단 → 설계 결함으로 에스컬레이션 → 수정 후 재감사 통과 전까지 해당 기능 배포 불가**

### 5-3. 성과 지표 측정 표준

| 지표 | 측정 쿼리 기준 | 목표 |
|------|--------------|------|
| 수집 성공률 | `DisclosureCollectionLog`: SUCCESS 건수 / 전체 건수 | ≥ 95% |
| 파싱 성공률 | `DisclosureDocument`: parseStatus='SUCCESS' / 전체 | ≥ 90% |
| 이벤트 분류 정확도 | 100건 수동 라벨 vs DB 대조 | ≥ 90% |
| 수치 추출 정확도 | 수기 계산 vs metricsJson 대조 | ≥ 85% |
| AI L0 비율 | 전체 공시 대비 AIUsageLog 미생성 비율 | ≥ 70% |
| AI 비용/건 | AIUsageLog 일별 평균 costUsd | < $0.005 |
| Exit Score 성능 | 50포지션 일괄 계산 시간 | ≤ 60초 |
| 신호 적중률 | BUY_CANDIDATE 후 D+5 수익 > 0% 비율 | ≥ 55% (M10) |
| Exit 정확도 | EXIT 후 D+3 추가 하락 비율 | ≥ 50% (M10), ≥ 55% (M12) |
| AI비용/모의순익 | AIUsageLog 합계 / PaperTrade 순익 | ≤ 20% (M10), ≤ 10% (M12) |
| MDD(백테스트) | BacktestRun.maxDrawdown | ≤ -15% |

### 5-4. 3대 원칙 QA 적용 방식

1. **"AI는 모든 공시에 쓰지 않는다"** → M3부터 매 마일스톤에서 L0 비율(≥ 70%) 및 일별 AI 비용 한도 준수를 측정·보고. 초과 시 게이트 차단.

2. **"매수보다 매도·포트폴리오 추적을 먼저 안전하게"** → M7·M8 테스트에서 PositionThesis.invalidConditions와 ExitSignal 트리거가 실제로 작동하는지를 M6(매수) 테스트보다 더 엄격한 시나리오로 검증.

3. **"자동매매는 마지막"** → M10 MVP 졸업 게이트를 QA가 공식 선언하기 전까지 M11 작업 착수를 차단. M12 자동매매 졸업 조건(90일 모의, 백테스트 3구간, Risk veto 검증)을 QA 보고서로 공식화.
